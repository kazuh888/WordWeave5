# GitHubを使った開発効率の試行計画

Status: 計画を文書化済み。今回この計画に基づくIssue作成・CI設定変更・PR作成は未実施。

## 狙いと範囲

テスト実行そのものをLLMから移すというより、課題の再調査、長い会話の再読、定型コマンドの組立て、ログ全文の読込みを減らす。GitHubへの移行だけで削減を保証しない。Issue更新やCI待ちの確認が増えれば逆効果になり得る。

「CIでテスト」と「PRでテスト」は、PRの作成・更新を契機にCIを実行する一つの仕組みとして扱う。現行リポジトリのCI・権限・費用条件は、導入着手時に確認し、既存設定を重複作成しない。

## 試行順序

1. [測定手順](kpi.md) に従い、取得範囲を確認する。同程度の小修正を現行方式でまず2～3件記録する。適切な既存計測があれば利用できるが、長期会話の累積値を基準にしない。
2. 導入範囲を確認してから、Issue・PR・Windows CIの試行を準備する。設定、権限、リモートへの書込みは別の明示的な導入作業とする。今回の文書化依頼を公開やpushの許可に読み替えない。
3. 同程度の小修正をGitHub方式でまず2～3件行う。同じ修正を二重実装せず、難易度・model/effort・検証範囲の違いを記録する。
4. 必要な検証と品質を維持した上で、消費・手戻り・所要時間を比較する。少数件の傾向であり、厳密な因果効果や一定の削減率を断定しない。範囲が揃わない測定は参考値とする。
5. Codexが継続・簡略化・見直しを提案する。導入時の消費と毎回の管理コストも別計上し、継続利用で回収できる見込みを評価する。

## 試行時の運用案

- 原則一つの開発タスクを一つのIssueにする。目的・対象外・完了条件・現状・残作業を短く維持し、毎回全コメントを読まない。大きな機能だけ分割する。
- ローカルでは変更箇所の回帰テスト、PRのWindows CIでは `cargo test --all-targets --locked` と `cargo build --release --locked --bin wordweave5` を候補とする。実行環境と対象commit、CIならhead/mergeどちらを検証したかを結果に残す。
- 既存の検証要件は試行計画だけで解除しない。CIとの分担を承認・設定した後に、同じ変更への不要な重複を減らす。失敗や関連修正後の必要な再実行は維持する。
- Codexは合否・件数を先に確認し、失敗時のみ関連ログを読む。継続監視は別途合意した場合だけ設定し、頻繁な状態確認を既定にしない。
- CIにCodex認証情報、実学習記録、録音・筆跡を投入しない。モック試験を使い、実IME・マイク・ペン・TTS・実Codexは別途受入とする。CI成功のみでIssueを受入完了にしない。
- 導入後の進捗の正本はIssueに寄せ、`tasks/current.md` は参照と最低限の再開情報にとどめる。試行前にローカルの残作業を削除しない。
- GitHub Actionsの実行時間・費用はLLMトークンとは別に記録する。通常のテスト実行と、追加のAIレビューサービスの消費も混同しない。
