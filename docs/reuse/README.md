**これは設計書であり、4機能すべてが独立ライブラリになったという完成報告ではない。** 「現行」は確認したソースの事実、「目標」は今後切り出す際の契約案（proposed）である。新しい型名・モジュール名は設計上の仮称であり、公開APIとして確定・実装済みではない。

## 1. この設計で決めること

音声評価、Codex app-server接続、Markdown表示、チャットを、必要な機能だけ選んで利用できる部品に分ける。教材・学習記録など、WordWeave固有の機能をこれらの技術部品へ持ち込まない。ソースをコピーして派生版を作る方式ではなく、同一の版を依存先として参照する方式を目指す。

将来の国語・理科学習ツール向けには、その上に学習進行のFrameworkを検討する。技術ライブラリと学習Frameworkは別の再利用単位であり、現行の英語アプリがそのままFrameworkとして使えるわけではない。今決める境界と第二教科で実証する条件は[Framework方針](framework.md)に記す。

最初の実利用先はWindows/Rustの単独音声評価ツールとWordWeave5とする。他言語や別の画面技術でも利用できる責任境界にするが、DLL・C ABI・HTTPサーバーを今から実装することは決めない。別言語の利用先が具体化した時点で、プロセス間通信などの接続方法を選ぶ。

## 3. 論理構成と依存方向

下図の名前は責任の単位であり、同数のCargo packageを直ちに作る指示ではない。

```text
利用アプリ（WordWeave5、単独音声評価ツール、将来の別ツール）
  ├─ 画面・通知・同意取得・保存先・アプリ固有処理
  ├─ chat-core ──→ アプリが実装する生成/保存/添付の窓口
  ├─ reading-evaluation ──→ Qwen接続部 ──→ HTTP通信
  ├─ codex-client ──→ 子プロセス・JSON-lines通信
  └─ markdown-egui ──→ Markdown解析部

組立て時だけ、アプリが各窓口へ具体的な接続部・保存部を渡す。
```

- 共通処理から `WordApp`、教材の `Entry`、学習状態の `Progress` を参照しない。
- 会話の管理はCodex/Qwenの具体的な通信実装を知らない。表示処理は会話・認証・通信を知らない。
- OS資格情報、ファイル保存、時計、通信、子プロセスは交換可能な境界に置く。すべての関数へ一律に抽象化を追加せず、試験や別アプリで交換する必要がある箇所に限定する。
- eguiの型を受け取るAPIは画面用部品に限定する。UIなしの利用者にフォント・画面・録音デバイスの初期化を要求しない。
- 最初は同一リポジトリ内で分離する。別リポジトリ、公開レジストリ、workspace変更は別の実装判断とする。

### CodexとQwenを無理に同一化しない

「任意のモデルに任意の入力を送る」単一関数を共通基盤の入口にしない。Codexの生成・exact IDによる再取得と、Qwenの音読評価は別の能力である。能力が不明な場合も、対応ありとは見なさない。

将来の選択は「チャットの生成」「教材案の生成」「音読評価」という用途から具体的な能力へ結び付ける。チャットと教材案は同じ接続部を使えても、プロンプト、構造検査、登録承認、上限の扱いは別である。今回、用途別設定の実装やQwenによるチャット・教材生成を追加するわけではない。

利用者はQwenにも明示的に対応する方向性を承認済みである。今回の文書作成では現行本体のCodex-only制約を変更せず、個別の実装方式・時期・実API試験・本体規約の更新を後続タスクで扱う。Qwenは利用者が明示的に選ぶ別経路として設計し、Codexの失敗時にAPIキー方式へ自動で切り替えない。[既存ADR](../decisions/0001-windows-harness.md)の「隠れた文脈を使わない」「AIに教材を書き込ませない」「結果不明で自動再生成しない」は引き続き守る。

## 4. アプリとライブラリの責任

| 対象 | ライブラリの責任 | アプリの責任 |
| --- | --- | --- |
| 送信する内容 | 検証済み・固定済みの入力だけを実行に使う | 対象ファイル・本文・送信先・目的を利用者へ示す |
| 送信の承認 | 承認対象と実入力の食い違い・重複実行を拒否する仕組みを用意する | 人の操作から承認を発行する。AI応答やMCP呼出しだけで承認しない |
| 認証 | 接続方式を明確にし、秘密をログ・結果へ出さない | 設定画面、資格情報の名前空間、アカウント選択を管理する |
| 結果 | 形式・識別子・上限を検査し、確認できた状態を返す | 表示、保存、教材等への適用を決める |
| 原文・原音 | 表示用変換と正本を区別し、勝手に補完・修正しない | 正本の保管、利用者による編集履歴、削除・バックアップを管理する |
| 教材登録 | 担当しない | 案、差分、承認、保存成功の確認を担当する |

### 承認と入力の固定

目標の公開入口では、検証した内容・宛先・用途・結果の受け渡し先を表す `PreparedRequest` と、ホストの人による操作に対応する承認を分ける。実行は承認時の内容で一度だけ開始し、元ファイルを再読込して違う内容へすり替えない。接続設定・資格情報もsnapshotまたは世代検査で対応付け、確認後に別アカウントへ黙って送らない。内容や宛先を変えた場合、接続設定の対応が失われた場合、再試行する場合は新たに確認する。秘密値そのものを確認表示やログへ載せない。

これは信頼されたアプリによる誤操作を防ぐ設計である。同一プロセスの悪意あるコードから人の同意を暗号学的に証明する仕組みではない。実際の人への確認はアプリの責任であり、ライブラリ導入時の適合試験で確認する。現行Qwenの公開 `evaluate` 自体にはこの承認APIはなく、GUI controllerが同意を担っている。切出し時に検討・実装する差分として扱う。

接続設定の検査対象はアプリが管理・観測できる範囲である。外部CLIの認証変更やサービス内部のアカウント切替まで常に検知できるとは約束しない。接続部ごとに確認できる識別情報と限界を示し、観測できない情報を一致済みと推測しない。

## 5. 結果・取消し・保存を混同しない

共通の巨大な状態enumを4機能へ強制するのではなく、以下の意味を各部品の契約に対応付ける。

| 判別する軸 | 例 | 禁止する解釈 |
| --- | --- | --- |
| ローカル処理 | 準備中、実行中、結果取得済み、待機を終了 | 待機終了をサーバー処理の取消しと断定する |
| 送信の確実性 | 未送信、送信済みの可能性あり | タイムアウトしたので未送信と断定する |
| 結果の確実性 | 検証済み結果、相手側の失敗を確認、結果不明 | 結果不明を再送して解消する |
| アプリでの反映 | 未保存、保存成功、保存失敗、適用保留 | AI生成成功を教材登録成功と表示する |

- 通信開始前に、少なくとも実行を識別できるローカル状態を確保する。永続化が必要なCodexの実行記録と、メモリのみのQwenセッションを一律に同じ保存方式へ変えない。
- 送信後のタイムアウト・取消し・異常終了は、課金や相手側処理の取消しを保証しない。自動再送は既定で行わない。
- 再取得と再生成は別APIにする。Codexは記録したthread/turnを特定して照会する。Qwenの現行MCP取得はメモリ内キャッシュの読出しであり、API側からの復旧機能ではない。
- アプリ終了時はそのアプリが所有する処理・子プロセスだけを終了・回収する。他のCodexや利用者のアプリを一括終了しない。
- ログ用の固定エラー分類と、利用者に示す説明を分ける。生のHTTP本文・プロンプト・キー・音声を共通ログへ自動記録しない。
- 指定モデル/effortと、サービスから実際に返った値を別に保持する。返却値がなければ未取得であり、指定値で埋めない。

## 6. 保存・安全・互換性

会話、音声、教材、実行記録の保管期間はアプリごとに決める。ライブラリが固定の `LOCALAPPDATA/WordWeave5` へ書き込むこと、原本を自動削除すること、別アプリの資格情報を暗黙に共有することは禁止する。既存データの保存形式は切出しだけでは変更しない。

公開API・保存形式・プロバイダーの通信形式には別々の版がある。通信形式の更新をアプリの保存形式更新へ直結させない。公開型を必要最小限にし、parser内部型、HTTPクライアント、WordWeaveの診断型を漏らさない。

初期版は実験的な0.xとして互換範囲を明記する。フィールド追加も、Rustの構造体リテラルや網羅match、厳密なJSON検査を壊す場合があるため、無条件に「後方互換」と扱わない。既存入口の互換ラッパー、移行例、契約試験を揃えてから置き換える。

依存ライブラリの更新、対応OSの拡大、利用規約・配布ライセンスの確認は切出し実装の受入条件に含める。既存の依存バージョンを設計書作成だけで変更しない。Web用UI、C ABI、汎用プラグイン機構は現時点で約束しない。

各段階は別の実装タスクとして承認を受ける。音声評価以外の独立した最小利用アプリはAPIの使いやすさを確認する試験用であり、二つ目の製品での実利用実績とは数えない。

最終的な再利用の合格は、**実際の二つの利用アプリがコピーなしで同じ部品を使い、片方固有の型・設定・保存先を必要としないこと**である。ビルドが通ることだけでは合格にしない。

## 9. Framework観点の見直しと次回の入口

今回の[仕様](../../tasks/FRAMEWORK-DESIGN-001/spec.md)・[計画](../../tasks/FRAMEWORK-DESIGN-001/plan.md)・[結果](../../tasks/FRAMEWORK-DESIGN-001/results.md)は初稿と分けて記録する。
既存4設計には教科横断利用の補足を加えた。学習用の試行記録・復習の仕組みは別のcore候補であり、技術部品からEntry/Progressへの依存を認める変更ではない。
第二教科の開発やライブラリ化を始めるplannerは、[Framework方針](framework.md)と[候補台帳](library-candidates.md)を先に確認する。保留項目は利用先・要件・失敗時契約が具体化した時点で再判定する。
技術部品の二消費者での実利用と、教科横断の縦断実証は別のgateである。どちらも今回の文書作成だけでは達成していない。
