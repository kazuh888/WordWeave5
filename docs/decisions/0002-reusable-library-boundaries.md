# 0002: 機能ごとに再利用境界を定め、二つの利用先で段階的に検証する

状態：設計方針案。2026-10-02 / REUSE-DESIGN-001。利用者は再利用設計の文書化を承認した。ライブラリの実装・公開API凍結・本体への新接続方式導入は別の実装タスクで扱う。

## 背景

音声評価、Markdown表示、Codex app-server接続、チャットを他のツールでも同じ実装で利用したいという要求がある。現在は一部の処理が分離されているが、ライブラリを呼ぶだけで画面・保存先・教材型まで必要になる箇所が残る。

Qwen音声評価はすでに独立したlib/binを持つ。一方、UIとWindows資格情報の依存も同じpackageにある。単にlib targetが存在することは、他アプリが必要な機能だけ利用できることの証拠ではない。

## 決定案

1. 今、Markdownを正本として[全体と4機能の設計](../reuse/README.md)を残す。HTMLが必要なら同じ原稿から生成する。実装済み・目標・未検証を分ける。
2. 単一の万能SDKではなく、音声評価、Codex接続、Markdown表示、会話管理の責任を分ける。package数はこの責任区分と同一に固定しない。
3. 処理、OS/通信/保存の接続部、画面を分ける。アプリが部品を組み立て、共通処理からWordWeave固有の型を参照させない。
4. 最初の実利用である単独音声ツールとWordWeave5から、同じ評価部品を呼ぶ。続いてMarkdown、Codex接続、チャットを必要な段階で切り出す。
5. 公開APIと互換性は各切出しで検証して確定する。別言語用のDLL/サービス、別リポジトリ、公開パッケージは利用先が具体化してから決める。
6. 利用者の送信許可、教材の案・差分・承認、原本の保持、結果不明時の自動再生成禁止を維持する。共通化を理由に権限を広げない。

## 代替案と採用しない理由

| 案 | 利点 | 今回採用しない理由 |
| --- | --- | --- |
| 組込み直前まで文書化しない | 初期の作業量が少ない | UI・保存先・認証の結合が残り、切出し時に責任を再発見する必要がある |
| 全機能を一つの汎用ライブラリにする | 入口が一つになる | Markdown表示だけの利用者にも通信や会話・OS依存を要求しやすい |
| 現行ソースを別ツールへコピーする | 最初の導入が速い | バグ修正・安全修正が分岐し、同一実装を流用する要求を満たさない |
| 全機能を最初からMCPサーバーにする | モデルから呼ぶ入口を揃えやすい | 画面描画や同一プロセスの部品利用には余分な通信境界となる。MCPの利用者とアプリSDKの利用者は同一とは限らない |
| 最初から全言語向けFFIを設計する | 呼出し言語を限定しない | 実際の利用先なしにメモリ所有・イベント・配布互換性の維持対象を増やす |

同じRust/eguiのアプリなら処理と表示部品の両方を利用できる。別UIでは処理を共用し、表示部を別に実装する。別言語ではさらに呼出し境界が必要になる。この条件が変わった時に設計を見直す。

## 既存ADRとの関係

[0001](0001-windows-harness.md)は現在のWordWeaveの所有・保存・承認方針を定める。本記録はこれを全面的に置換しない。Qwenへの明示的な対応方向は利用者承認済みであり、Codexの認証失敗をAPIキー方式で代用するフォールバックではない。具体的な組込み方式・時期・実API試験・規約更新は今回の文書作成承認に含めず、後続タスクで扱う。今回AGENTS.md、本体認証設定、保存形式は変更しない。

## 影響と完了条件

設計書と契約試験の維持コストは増える。反面、接続、表示、会話の変更を利用アプリへ無差別に波及させずに済む。共通処理へ一つ目のアプリ固有の都合を入れないため、第二の利用者による実証が必要である。

文書段階は根拠、責任、異常系、互換性、移行条件が追跡できれば完了できる。ライブラリ段階は実際の二つのアプリが同じ部品をコピーなしで利用し、個別の承認・保存方針を守ることを確認して完了とする。モック試験や最小サンプルだけを二製品での実利用とみなさない。

音声モデルの助言品質、Codexの実認証、OSの資格情報保護、日本語フォントの実描画は、それぞれ別の受入証拠を必要とする。設計レビューだけで検証済みにしない。
